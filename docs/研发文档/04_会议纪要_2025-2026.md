### 会议 #M2025-003：模型迭代评审

| 项目 | 内容 |
|------|------|
| **时间** | 2025年2月14日 14:00-15:00 |
| **地点** | 人工智能实验室3F-312 |
| **主持人** | 李工 |
| **参会人** | 算法组全员 + 张老师 |
| **会议类型** | 技术评审 |

#### 核心数据

**李工**汇报实验结果（实验 #E2025-001）：

> YOLOv5m + 方案B（适度数据增强）最优：
> - mAP@0.5: 0.891（比基线+1.8%）
> - mAP@0.5:0.95: 0.679
> - 训练耗时：7.8h
> - 推理速度：22ms/张

> U-Net BCE+Dice组合损失：
> - IoU: 0.802（比纯BCE +2.1%）
> - Dice: 0.881

**张老师**：精度提升不错。但为什么激进增强方案C反而效果差？

**李工**：我们分析是过增强问题。方案C的旋转±30°和Cutout对划痕这种细长缺陷特别不友好——旋转后划痕方向变了，Cutout可能直接把缺陷区域抹掉了。所以方案B的±15°是最合适的。

**陈工**：数据那边新增的28张样本标注完了吗？

**李工**：已经标注完成并加入训练集。这批样本主要是坑洞387-389和溢胶214-216，质量不错。

#### 决议
- ✅ 正式采用YOLOv5m+方案B作为检测基线
- ✅ 正式采用BCE+Dice Loss作为分割损失函数
- ✅ 数据组继续扩充样本，目标Q2达到5000张

### 会议 #M2025-005：AI大模型接入方案评审

| 项目 | 内容 |
|------|------|
| **时间** | 2025年4月2日 14:00-15:30 |
| **地点** | 人工智能实验室3F-312 |
| **主持人** | 李工 |
| **参会人** | 全员 |
| **会议类型** | 技术方案评审 |

#### 背景

V1.3的核心目标是让检测报告"会说话"——不是简单列出数据，而是能基于数据给出产线优化建议。这需要接入大模型。

#### 候选方案

| 方案 | 模型 | 成本 | 网络依赖 | 分析质量 |
|------|------|------|----------|----------|
| A | 讯飞星火 Spark v3.5 | 按Token | 需要 | ★★★★ |
| B | OpenAI GPT-4o | 较高 | 需要 | ★★★★★ |
| C | 本地Ollama (Qwen) | 免费 | 不需要 | ★★★ |

**李工**：我倾向星火。理由三个：一是中文优化最好，我们分析报告全是中文；二是成本可控；三是团队之前用过星火API，有经验。

**王工**：OpenAI的问题是网络——产线环境可能没有外网，或者网络不稳定。而且API费用长期来看不低。

**张老师**：本地部署Ollama的方案呢？能省掉网络依赖。

**李工**：本地部署的问题是模型质量和硬件要求。实验室的4070跑检测已经占了不少显存，再跑一个大模型可能不够。而且小参数模型的分析质量明显不如云端大模型。

**赵工**：能不能做混合方案？默认用星火，如果网络不通就降级到本地小模型或预设建议？

#### 决议
- ✅ 主方案：讯飞星火Spark v3.5 API
- ✅ 降级方案：网络超时3次后使用预设建议文案
- ✅ 后期评估Ollama本地部署可行性（作为2026年技术储备）
- ✅ Prompt模板由李工和王工联合设计

#### Prompt设计原则
1. 以"根据检测数据"开头，确保逻辑连贯
2. 限定200字以内，避免过于冗长
3. 聚焦"可以做什么"而非"问题是什么"
4. 以"通过以上措施，有望提高生产线的效率和产品质量"结尾，形成闭环

### 会议 #M2026-001：Jetson Orin边缘部署技术方案

| 项目 | 内容 |
|------|------|
| **时间** | 2026年1月5日 10:00-11:30 |
| **地点** | 人工智能实验室3F-312 |
| **主持人** | 李工 |
| **参会人** | 李工、王工、陈工、张老师 |
| **会议类型** | 技术方案评审 |

#### 背景

V2.2部署在配备RTX 4070的PC上。但对于产线环境，需要更小型、更低功耗的边缘设备。选用Jetson Orin AGX 32GB作为目标平台。

#### 环境搭建方案

| 组件 | 版本 | 备注 |
|------|------|------|
| JetPack | 6.0 | 含CUDA 12.2 + TensorRT 8.6 |
| PyTorch | 2.2.0 (Jetson专用版) | torchvision 0.17 |
| OpenCV | 4.8.0 (with CUDA) | JetPack自带 |
| ONNX Runtime | 1.17.1 | U-Net推理备用 |

#### YOLOv5 → TensorRT转换流程

```
best.pt → ONNX → TensorRT Engine (.trt)
         ↓ (onnxsim优化)
      ONNX(simplified) → TensorRT Engine
```

**李工**：转换成功，FP16下18ms/张。但U-Net的upsample层TensorRT不支持。

**王工**：U-Net暂用ONNX Runtime，比PyTorch快26%（48→38ms）。等NVIDIA修复或我们自己实现upsample plugin。

#### 决议
- ✅ Jetson Orin作为边缘部署目标平台
- ✅ YOLOv5走TensorRT FP16（18ms）
- ✅ U-Net暂走ONNX Runtime（38ms）
- ✅ 后续自研TensorRT upsample plugin

### 会议 #M2026-002：多产线架构设计

| 项目 | 内容 |

#### 设计目标

支持单台服务器同时接入4路产线视频流，每路独立检测、独立报告。

#### 架构方案

**王工**提出多进程方案：
```
Main Process (管理进程)
  ├── Worker Process 1 (产线1: 视频采集 + 检测 + 报告)
  ├── Worker Process 2 (产线2: 视频采集 + 检测 + 报告)
  ├── Worker Process 3 (产线3: 视频采集 + 检测 + 报告)
  └── Worker Process 4 (产线4: 视频采集 + 检测 + 报告)
```

- ✅ 采用多进程架构，每产线独立Worker
- ✅ 模型权重使用共享内存（减少显存占用）

### 会议 #M2026-003：3D检测技术调研汇报

| 项目 | 内容 |
|------|------|
| **时间** | 2026年3月9日 14:00-15:30 |
| **地点** | 人工智能实验室3F-312 |
| **主持人** | 李工 |
| **参会人** | 算法组 + 张老师 |
| **会议类型** | 技术调研汇报 |

#### 三种3D方案对比

| 方案 | 原理 | 精度 | 速度 | 成本 | 适用场景 |
|------|------|------|------|------|----------|
| 结构光 | 投射条纹图案 | 0.01mm | 慢(>1s) | 高(>5万) | 超高精度检测 |
| 激光三角法 | 激光线扫描 | 0.05mm | 中(~200ms) | 中(~1万) | 轮廓检测 |
| 双目视觉 | 双摄像头视差 | 0.1mm | 快(~30ms) | 低(~2千) | 深度方向缺陷 |

#### 原型实验结果

**李工**：
> 我们用Intel RealSense D455（双目+结构光混合）做了初步实验（实验 #E2025-011）：
> - 凹陷检测AP：0.891（2D检测仅0.723）
> - 凸起检测AP：0.902（2D检测仅0.756）
> - 联合检测AP：0.934
>
> 结论很明确：深度方向的缺陷，3D检测远超2D。但2D在崩边这类边缘缺陷上依然有优势。

**张老师**：成本方面呢？工厂能接受吗？

**李工**：RealSense D455约3000元，产线部署的话每路增加成本可以接受。但如果用结构光方案就贵了。

#### 决议
- ✅ 3D检测作为V3.0核心特性之一
- ✅ 先基于RealSense D455方案推进
- ✅ 2D+3D联合检测架构设计列入Sprint 18
- ✅ PointNet作为3D特征提取基线

#### 测试概况
- 时间：2026年5月14日-17日（72小时连续运行）
- 地点：合作工厂2号产线
- 检测对象：钢化玻璃面板（5种型号）
- 产线速度：1.5-2.0m/s
- 检测量：约12,000片
- 准确率：90.5%（对比人工抽检）

#### 问题与改进

**工厂李厂长**：
> 系统整体不错，检测准确率比我们预期的高。但有两个问题：
> 1. 高速时(>2m/s)会漏掉一些缺陷——传送带太快，相机没来得及拍
> 2. 车间灰尘大，镜头半天就脏了，影响检测结果

**李工**：
> 第一个问题我们分析了——目前的方案是软件定时触发拍照，在高速下帧率跟不上。
> 改进方案：用光电传感器硬件触发，检测到板材经过时发GPIO信号触发相机拍照。
> 这个方案响应时间<1ms，理论上支持到3m/s的产线速度。

**赵工**：
> 灰尘问题可以加装气帘或者定期自动清洁装置。另外咱们可以在检测前加一帧"空拍"做背景减除，减少灰尘干扰。

**王工段长**：
> 另外操作界面能再简单些吗？我们产线工人文化程度不高，现在那个设置界面选项太多。

**张老师**：这个反馈很好。我们可以做一个"简易模式"——只显示检测开始/停止和结果，其他配置隐藏。

#### 决议
- ✅ 硬件触发拍照方案立即推进，Sprint 20完成
- ✅ 工业相机（海康MV-CS系列）SDK接入
- ✅ 增加"简易模式"UI，V2.2.6实现
- ✅ 镜头防尘方案（气帘）评估
